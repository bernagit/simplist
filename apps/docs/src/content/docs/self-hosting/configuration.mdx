Nel deploy Docker tutta la configurazione sta nel file `.env` accanto a `compose.yaml`. Il file lo leggono sia Docker Compose (immagini, porta, database) sia l'API (`env_file`). Dopo una modifica, applicala con `docker compose up -d`.

La web app non ha configurazione: in produzione parla con l'API sullo stesso dominio, tramite il proxy.

## Generale

| Variabile | Predefinito | Descrizione |
|---|---|---|
| `VERSION` | `latest` | Versione delle immagini da usare (per esempio `0.7.4`). Usata solo da Docker Compose. |
| `HTTP_PORT` | `3000` | Porta dell'host su cui risponde il proxy. Usata solo da Docker Compose. |
| `COMPOSE_PROFILES` | — | Servizi facoltativi da avviare: `docs` aggiunge la documentazione su `/docs/`. |
| `KEYS_DIR` | `./keys` | Cartella dell'host con i segreti dell'API (chiavi di sessione e delle notifiche). Usata solo da Docker Compose. |
| `REGISTRY` | `ghcr.io/bernagit` | Registry delle immagini. Usata solo da Docker Compose. |
| `APP_URL` | `http://localhost:3000` | Indirizzo pubblico dell'istanza. Serve per i link nelle email, per il link del primo utente e per gli inviti. |
| `CORS_ORIGIN` | `http://localhost:3000` | Origine consentita per le chiamate all'API. Impostala uguale ad `APP_URL`. |
| `PORT` | `2000` | Porta dell'API dentro il container. Non cambiarla nel deploy Docker: il proxy la cerca lì. |
| `LOG_LEVEL` | `info` | `error`, `warn`, `info` o `debug`. |

## Database

| Variabile | Predefinito | Descrizione |
|---|---|---|
| `POSTGRES_USER` | `postgres` | Utente PostgreSQL. Lo usa anche il container `db` per inizializzare il database. |
| `POSTGRES_PASSWORD` | — | Password PostgreSQL. Obbligatoria. |
| `POSTGRES_DB` | `simplist` | Nome del database. |
| `POSTGRES_VOLUME` | `simplist_postgres_data` | Volume Docker con i dati del database. Serve solo per riusare il volume di un'installazione precedente (vedi [Aggiornamenti e backup](/docs/self-hosting/maintenance/#passare-al-nuovo-compose)). |
| `POSTGRES_HOST`, `POSTGRES_PORT` | `db`, `5432` | Indirizzo del database. Nel deploy Docker li imposta `compose.yaml`: servono solo senza Docker. |
| `DATABASE_URL` | — | In alternativa alle variabili sopra: URL completo (`postgresql://utente:password@host:5432/db`). Se è impostata, ha la precedenza. |

<Aside type="caution">
`POSTGRES_PASSWORD` viene usata per creare il database **solo al primo avvio**. Se la cambi in seguito, devi cambiarla anche dentro PostgreSQL (`ALTER USER … PASSWORD …`), altrimenti l'API non riesce più a connettersi.
</Aside>

All'avvio l'API applica da sola le migrazioni del database: non serve nessun comando per creare le tabelle o aggiornarle.

## Sessioni

| Variabile | Predefinito | Descrizione |
|---|---|---|
| `JWT_EXPIRES_IN` | `6h` | Durata del token di accesso. Viene rinnovato in automatico finché la sessione è valida. |
| `REFRESH_TOKEN_EXPIRES_IN_DAYS` | `30` | Giorni dopo i quali, senza usare l'app, bisogna rifare l'accesso. |
| `COOKIE_SECURE` | `true` | Cookie solo su HTTPS. Mettila a `false` solo per un'istanza servita in HTTP, per esempio su una rete locale. |

Le chiavi che firmano le sessioni (coppia EC P-384, algoritmo ES384) le crea l'API al primo avvio in `keys/private.key` e `keys/public.pem`, nella cartella montata in `/app/keys`. Se usi un sistema per i segreti, puoi passarle invece con le variabili `JWT_PRIVATE_KEY` e `JWT_PUBLIC_KEY` (in formato PEM): in quel caso i file non vengono creati.

## Registrazione e inviti

| Variabile | Predefinito | Descrizione |
|---|---|---|
| `INVITE_PER_USER` | illimitati | Numero massimo di inviti che ogni utente può creare. |

La registrazione è solo su invito. Un invito vale **7 giorni** e si usa una volta sola. L'invito per il primo utente è un'eccezione: vale un'ora.

## Email

Tutte facoltative. L'email si attiva solo se ci sono **tutte** le prime cinque variabili. In quel caso l'API verifica la connessione all'avvio: se la verifica fallisce lo segnala nei log e parte comunque, senza email funzionanti finché il server SMTP non risponde.

| Variabile | Predefinito | Descrizione |
|---|---|---|
| `SMTP_HOST` | — | Server SMTP. |
| `SMTP_PORT` | — | Porta, di solito `587` (STARTTLS) o `465` (TLS). |
| `SMTP_USER` | — | Utente SMTP. |
| `SMTP_PASS` | — | Password SMTP. |
| `MAIL_FROM_EMAIL` | — | Mittente delle email (per esempio `no-reply@esempio.it`). |
| `SMTP_SECURE` | `false` | `true` per una connessione TLS diretta (porta `465`). |
| `MAIL_FROM_NAME` | `Simplist` | Nome del mittente. |

Senza email non vengono inviati l'email di benvenuto, gli inviti via email e il recupero della password. Tutto il resto funziona.

## Notifiche push

| Variabile | Predefinito | Descrizione |
|---|---|---|
| `VAPID_PUBLIC_KEY` | generata | Chiave pubblica VAPID, da impostare solo per usare una coppia tua. |
| `VAPID_PRIVATE_KEY` | generata | Chiave privata VAPID, insieme alla pubblica. |
| `VAPID_SUBJECT` | `mailto:` + `MAIL_FROM_EMAIL`, altrimenti `APP_URL` | Contatto inviato ai servizi push: `mailto:` oppure un URL `https://`. |

Non serve configurare niente: al primo avvio l'API crea le chiavi VAPID in `keys/vapid.json`. Conservale con i backup: se cambiano, ogni dispositivo deve riattivare le notifiche.

I promemoria partono dall'API, che ogni minuto controlla quelli in scadenza. Anche con più istanze dell'API ogni promemoria viene inviato una sola volta.
